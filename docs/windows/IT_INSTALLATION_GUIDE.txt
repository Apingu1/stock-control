STKFLO
WINDOWS INSTALLATION & REMOTE MANAGEMENT GUIDE

PACKAGE
-------
Build with BUILD_COMMERCIAL_PACKAGE.bat from the approved source.
Distribute the complete StkFlo-Windows-Installation.zip to a controlled
network share (such as N:). The package contains:
  01 - INSTALL SERVER.bat
  02 - START SERVER.bat
  03 - STOP SERVER.bat
  04 - SERVER STATUS.bat
  05 - PUBLISH CLIENT DEPLOYMENT.bat
  06 - UPDATE SERVER.bat (existing installations, preserves data)
  CLIENT DEPLOYMENT
  Administration & Recovery
  HOST MANAGEMENT
  Documentation
  System

SERVER INSTALLATION
-------------------
Run 01 - INSTALL SERVER.bat directly from the network share on the
Windows 11 VM. It stages the entire release locally BEFORE UAC elevation.
The live server is installed to C:\ProgramData\StkFlo\Server.
Only the server needs Docker Desktop and Docker/Windows administration.
On a fresh test installation, StkFlo provisions the temporary login
  Username: admin
  Temporary password: Admin123!
The final ORIGINAL N: installer window clearly displays the credentials
after the server and shared CLIENT DEPLOYMENT folder are both verified.
Do not close the original window before recording the final login summary.
A password change is REQUIRED immediately at first sign-in.
An existing real administrator account is never silently reset on upgrade;
the original window says the existing password was retained.
This fixed known password is for controlled testing only. Use a unique
installer-generated secret before production deployment.
The application is then available at https://stkflo/ on HTTPS 443.
Keep the proven Hyper-V/VM IP configuration and Docker auto-login unchanged.
During an installation launched directly from N:, the elevated VM setup
first creates C:\ProgramData\StkFlo\Server\client-deployment\client-config.ini
with the actual confirmed VM IPv4 address and the real public CA .crt.
It then RETURNS AUTOMATICALLY to the original non-elevated launcher,
which publishes those two files to the exact CLIENT DEPLOYMENT folder
beside the N:\...\01 - INSTALL SERVER.bat that was launched.
The final success message appears ONLY after the N: copy and hash checks.
Do not close the original install window before this final message.
If publication fails (e.g. N: share write permissions), do not reinstall.
On the Windows VM run 05 - PUBLISH CLIENT DEPLOYMENT.bat from the package root
under an account with write access to the shared release folder. A READY
marker must be present before distributing the client installer.
Never distribute server private .key files.

UPDATE AN EXISTING SERVER (NO REINSTALL)
----------------------------------------
From the newest approved StkFlo-Windows-Installation.zip, extract the
complete release to the approved network share (N: or UNC).
On the existing Windows VM, double-click:
  06 - UPDATE SERVER.bat
This updater stages files locally before administrator elevation, opens a
visible administrator CMD window (same as the original StkFlo installer),
verifies that the existing server and PostgreSQL container are running,
and runs the
existing verified StkFlo backup engine BEFORE any code is overwritten,
saves a source rollback copy, then rebuilds API and web containers.

The updater specifically DOES NOT run 01 - INSTALL SERVER.bat, uninstall,
database reset, Docker volume removal, certificate regeneration or admin
password bootstrap. Existing records, .env credentials, TLS keys and client
deployment configuration remain on the installed VM. It will stop on a
failed database backup, Docker validation, image build or health check.
See deployment\\update-history for logs, and
deployment\\update-source-rollback for pre-update source copies.

Run updates in an approved maintenance window. Check backup location and
successful recovery tests before go-live. If the update fails, the
administrator CMD window stays open and prints the failure. Read the full
transcript under deployment\update-history before retrying. The updater
never runs the fresh-install routine as a fallback.
After a successful update, verify
the dashboard, all materials, new-material numbering, receipts, consumption,
lots and Product BMR records on the same database. Client reinstall is NOT
required for a standard server-only application update.

CLIENT INSTALLATION
-------------------
After server installation, run CLIENT DEPLOYMENT\01 - INSTALL CLIENT.bat
directly from N: on each staff workstation. It also stages locally before
elevation. Clients do not need Docker or Python. They use a trusted public
StkFlo CA, approved hostname mapping, a common desktop shortcut, and their
individual StkFlo login credentials.

INDEPENDENT RECOVERY
--------------------
On the PHYSICAL Hyper-V host, run:
  HOST MANAGEMENT\01 - INSTALL HOST MANAGER.bat
On the Windows 11 VM, run:
  Administration & Recovery\03 - ENABLE VM MANAGEMENT.bat
These one-time installers configure HTTPS Windows-authenticated management
tasks independent of Docker. An approved Windows identity, network CIDR,
and the actual Hyper-V VM/Docker user are required.
Authorised admin URLs:
  https://stkflo-host:9443/  (VM power recovery, physical host)
  https://stkflo-manager:9444/ (Docker stack and backup share, VM)
Create corresponding DNS/hosts entries and trust the verified PUBLIC
manager certificates on authorised administrative computers.

BACKUP TO THE EXISTING CLOUD-BACKED N: SHARE
-------------------------------------------
Database dumps are first created and SHA-256-verified in the VM-local
C:\ProgramData\StkFlo\Server\Backups folder.
From the VM Manager configure the real \\server\share UNC backup path,
NOT the N: drive letter. The dedicated Windows task verifies copies on
the share every 15 minutes; the existing cloud backup of the share provides
off-host protection. StkFlo Admin controls backup time/retention and reports
replication health. Test real database recovery before going live.

See Documentation\STKFLO_WINDOWS_REMOTE_MANAGEMENT.md for detailed
network, certificate, security, installation and acceptance instructions.

SAFEGUARDS
----------
Force VM reset is disabled by default. Remote actions require Windows
membership, HTTPS and a recorded reason. StkFlo manager pages remain
reachable when Docker is stopped but not when their own Windows machine
is powered off. A physical host outage requires independent IT recovery.

The test uninstall removes VM-local StkFlo data/volumes only after explicit
confirmation; it does NOT delete the shared N: distribution package or
external cloud-backed backup files.

All new Windows functionality must be tested on the actual host and VM,
with approved change control, before production use.
